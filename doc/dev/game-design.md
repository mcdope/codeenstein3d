# Game Design

This is the developer-facing "why" behind Codeenstein 3D's design — for the player-facing "how", see [`doc/user/mechanics.md`](../user/mechanics.md); for exact current numbers (HP multipliers, aggro radii, drop rates), see that doc or the source directly, since they change as balancing continues.

## Everything maps to something

The core design principle is that every construct the parser can extract from a source file should become *something* in the level, rather than being silently dropped — a codebase should feel fully translated, not partially. Concretely:

- **Functions/methods → enemies.** HP scales with cyclomatic complexity, so a genuinely tangled function is a harder fight than a simple one — the game's difficulty curve is, by design, a reflection of the codebase's own complexity rather than a hand-tuned level progression. A function with its own code smells (more than 5 params, or nesting more than 3 levels deep) gets a scaled HP bonus on top of the base complexity number — the smell itself, not just the branching that produced it, is treated as something worth fighting harder.
- **Global variables → hazard rooms**, not enemies. Globals aren't "doing" anything the way a function is; they represent ambient, code-smell-adjacent state, which reads better as an environmental hazard (an acid pool) than as something you fight and defeat.
- **Private/protected methods → key-locked rooms.** Encapsulation becomes a literal locked door — access modifiers already express "you're not supposed to reach this directly," which maps naturally onto needing a key.
- **`goto`/label pairs → teleporters**, in the spirit of Unreal Tournament jump pads: a `goto` is already a non-linear jump in control flow, so a bidirectional teleporter pair is a fairly direct translation rather than a stretch.
- **Code smells that hide something → secret rooms.** Originally just dead code (unreachable statements after a `return`) — narratively, code that can never execute is a hidden space the codebase itself doesn't know is there, fitting for a secret behind a fake wall with better loot. Dead code alone turned out to be too rare a trigger in clean, well-tested codebases, so the pattern was broadened to four more "the code is hiding something" smells: an empty/swallowed-exception catch block, a `@deprecated`/`[Obsolete]`-style marker, a commented-out code block (or an oversized comment block generally), and a magic-number/blob literal (a long Base64-ish string, or a well-known hex constant like `0xDEADBEEF`). All five feed the same capped, fairly-sampled, one-per-room pool of secret-room slots per level (see `placeSecretRooms` in `src/map/generation/secretRooms.ts`), and the level-start briefing now surfaces the resulting count so a player knows there's something to look for. Loot is picked uniformly among whatever's actually available that run — health and armor are always in the running, rockets once the launcher's owned, and a still-unowned gdb/ghidra/Friday Hotfix outright (plus, from campaign level 4 on, Toolchain) — rather than the original two-way health/rockets coinflip, which collapsed to "always health" for any player who hadn't unlocked the launcher yet.
- **Large comments → lore terminals.** A big comment is the author speaking directly to a future reader; surfacing it as an interactable in-world text panel keeps that voice intact instead of discarding it. TODO/FIXME comments are deliberately exempted from the normal length gate (even a one-line `// TODO: fix this` gets a terminal) because that's the most common real-world form of technical debt, and excluding short ones would miss most of what this feature exists to surface — each one also spawns a small "technical debt" encounter (trap, mine, or a weak "Bug" enemy) on the approach, rather than a permanent hazard, since the terminal has to be reachable to read — kept at least a minimum distance from the player's spawn point, same as every other hazard placement, so a TODO comment that happens to sit in the spawn room can't ambush the player before they can react (see [Hazard Placement Spawn Safety](decisions.md#hazard-placement-spawn-safety)). License/copyright headers are excluded on purpose — they're boilerplate, not authored lore, and would otherwise turn nearly every file into a terminal.
- **`switch`/`match` → Switchboard junctions.** Branching control flow becomes branching *geometry*: the function's own room turns into a hub with one short dead-end spur per `case`. The `default` branch deliberately gets no spur of its own — it's the branch that falls through to whatever comes next, and the hub is already wired into the rest of the level, so "the default path continues the level" is true by construction rather than by special-casing. Capped at five spurs (and two per wall) so a `switch` over a thirty-value enum reads as a junction rather than a starburst. Each spur is behind a *keyless* branch door, not the key-locked kind: a switch's internal branching is control flow, not encapsulation, and treating it as encapsulation would both be wrong in-fiction and bury a private method's level in doors and keys.
- **`try`/`catch`/`finally` → a risk→recovery→reward gauntlet.** The three clauses already describe a sequence with a shape, so the level follows it literally: the `try` is a narrow acid corridor with traps you *will* take damage crossing, the `catch` is an alcove at the far end that hands back health and armor, and the `finally` is the safe room past it that pays out whatever happens. The catch alcove stocks both restoration kinds rather than rolling between them, because health clamps at full — a player who came through the gauntlet unhurt would otherwise find a "guaranteed" reward doing nothing.
- **Imports → Vendor Depots.** The third-party code a file leans on becomes the third-party supplies you start the level leaning on: small alcoves built straight into the spawn room's wall, one per few imports. They're the one hazard-free construct here, deliberately — they sit where the player stands in the first seconds of a level, which is exactly where [Hazard Placement Spawn Safety](decisions.md#hazard-placement-spawn-safety) says nothing dangerous belongs.
- **Heavy allocation → a room that leaks.** A function that allocates densely gets a room whose floor floods with acid the moment you walk in, and keeps flooding until you kill the enemy that function spawned. It's the one construct that maps to an *event* rather than to terrain: a leak is something happening over time, not something that's simply there, and making the fix "kill the thing that's leaking" is the most direct translation of the fiction there is. Being an event is also why it's the only map feature with its own alert — everything else in a level is *there* to be noticed at the player's own pace, but a flood that starts behind you needs to announce itself, or taking damage reads as an unfair hit rather than as a mechanic. Both a floor on the raw count and a per-line density gate have to pass, so neither a three-line helper with one `new` nor a thousand-line module with five scattered allocations qualifies.
- **`.h` files → bonus levels.** A header is usually a smaller, self-contained, single-purpose file compared to its implementation — a natural fit for a shorter "restock" level with boosted pickup rates, discovered "by accident" during playtesting rather than planned from the start.

## Enemy and difficulty philosophy

A function's cyclomatic complexity converts to HP at a fixed rate; beyond a certain size, complexity is expressed as *more* enemies (a "pack") rather than one increasingly bloated HP pool, so a big function reads as "this does a lot" rather than "this is a damage sponge." Past an extreme complexity threshold the encounter changes tier rather than just scale: the room's budget doubles and it spawns an Elite pack led by a boss-tier Elite — more damage, a guaranteed health/ammo drop plus a high-odds extra weapon drop, a distinct look — marking a genuinely different kind of code, not just "a really big pile of the same thing." The pack stays a pack, though: no enemy is ever bigger than *one* player can actually kill, so a boss fight is a fight you can lose rather than one you cannot win, and it gets easier as you cut the pack down. **Coop is the deliberate exception.** Elite HP and damage scale with player count, and past two players that pushes the anchor above the ceiling a solo run is calibrated against — on purpose, because an Elite tuned for one player is trivial for four, and an encounter anybody can solo is not a coop encounter. The point is a pack the *team* has to commit to together; everything else on this page describes the single-player calibration. See [Enemy Scaling](decisions.md#enemy-scaling-packs-vs-elites) for how this threshold was chosen, what playtest telemetry corrected about it, and why the coop multiplier is a placeholder rather than a measured value.

Easy/Normal/Hard scale three axes in the same direction on purpose: Hard makes enemies tougher, deal more damage, *and* aim straighter, while simultaneously making ammo/health/armor scarcer — the effects compound rather than offset, so difficulty isn't just "bullet sponges," it's a genuinely tighter resource margin and a sharper threat too. Easy mirrors most of this in reverse, but not damage dealt one-for-one with its HP reduction: balance telemetry (a 450-run, 9-combo campaign) found Easy's original mirrored curve, combined with a cautious/health-seeking playstyle, could produce near-total immunity for an entire 17-level campaign — real stakes on Easy needed the damage floor raised independently of the HP floor, so `DIFFICULTY_MULTIPLIERS.easy.damage` (0.85) no longer mirrors `.hp` (0.7) the way Hard's pair still does.

Enemy aim is the third axis, added after that same telemetry found accuracy sitting in a narrow ~70-77% band regardless of difficulty tier — enemies had *zero* aim deviation at all, so difficulty's whole bite was HP/damage, never actually "smarter." Ranged bolts now roll a random deviation off dead-center, up to a per-difficulty cap (`enemyAimSpreadDeg`: 10°/4°/0° for easy/normal/hard) — Hard's 0° keeps enemies aiming exactly as precisely as they always did (a bolt still isn't hitscan or homing, so it stays dodgeable), while Easy/Normal enemies now genuinely aim worse rather than just hitting proportionally softer.

Every other enemy exists *because* of something the parser found (a function, a TODO comment); the Edge Case is the one exception — it's a pacing fix, not a code-mapping one. (Since 2026-08-20 it has a second, smaller role: a `switch`-heavy function's room may trade its tail pack member for one, so a branchy function reads as a scatter of small cases around one real body. That use *is* code-mapped; the corridor one still isn't.) Long, empty corridors read as boring "endless walk" filler no matter how well the rest of the level maps to the source, so corridors get dressed with enclosed spaces — a baffled room, a pillared hall, a gateway, a plaza, a pair of alcoves — and each of those is populated with 1-3 Edge Cases: small, fast, jarringly cyan-tinted, barely-any-HP nuisances that read as a literal "bug in the system" rather than a real threat. The geometric half (shorter corridors) and the gameplay half (something to shoot on the way through) are deliberately both present rather than either alone, since neither one fully solves "the walk feels empty" by itself.

**That pairing is why corridor dressing has two passes rather than one.** The original single pass only fired on runs past a length threshold, which was the right trigger while corridors were enormous. Once room placement was reworked to pack rooms together, corridors got short enough that the threshold stopped being crossed — six times across the whole demo campaign — and the geometric half of the fix would have silently deleted the gameplay half with it, since Edge Cases spawn in these rooms and nowhere else. `dressCorridors` therefore also spends a room-count-scaled ornament budget on corridors that are already short enough, purely so corridors keep having something in them. See [Corridor Dressing: A Vocabulary, Best-Effort](decisions.md#corridor-dressing-a-vocabulary-best-effort).

## Weapon and economy intent

Ammo is split into five pools (bullets, shells, smg, rockets, gas) specifically so each weapon has a distinct resource identity rather than one shared pool making every gun interchangeable. gdb originally shared the bullets pool with the pistol/shotgun — split out into its own `"smg"` pool once that stopped reading as a distinct resource identity in practice: a full-auto weapon burning through a shared pool at ~11 rounds/sec meant a single pickup sized for a precise pistol shot (6 bullets) drained in under a second, and diluted the "each weapon should feel distinct" intent this section already committed to. Its own pool gets its own drop size (`SMG_DROP_AMOUNT`, 21 — a burst, not a bullet) instead. Friday Hotfix (the flamethrower, unlocked at campaign level 12) followed suit from day one with its own `"gas"` pool (`GAS_DROP_AMOUNT`, also 21) rather than repeating gdb's original mistake. The **shotgun** was the last weapon still sharing `bullets`, and the same argument applied to it a third time: 4 bullets a pull out of the pistol's pool meant the two starting weapons competed for one resource, so favouring either one disarmed the other. It now spends 1 `"shells"` per pull from its own pool (`SHELLS_DROP_AMOUNT`, 2 — one full magazine), which is also what lets a magazine size mean anything for it. gdb, ghidra, and Friday Hotfix are all gated behind an unlock (an Elite kill, or a forced grant at fixed campaign milestones as a safety net) — giving any of them out from the start would make an Elite's guaranteed drop meaningless, and rolling their ammo before the weapon is owned would just be a dead, wasted drop. Toolchain (the chainsaw that replaces the knife once found) deliberately breaks that pattern rather than extending it: it has no forced-unlock milestone at all, and isn't reachable through the ordinary per-kill roll either — only a secret room, an Elite kill, or a small independent chance riding on an otherwise-empty regular-kill roll (see below) — all from campaign level 4 on — a genuinely missable unlock, not a "you'll definitely have it by level N" guarantee like the other three. Where gdb (full-auto hitscan) and ghidra (splash-damage projectile) each cover a distinct combat role, Friday Hotfix instead leans into being a point-blank melter that's nearly useless at range, giving the campaign's latest unlock a genuinely different identity from "gdb but stronger." Cone spread alone didn't sell that short range in playtesting — pellets could still land well past a real flamethrower's reach even with a *narrower* cone than the shotgun's — so it also carries its own range curve — full damage to `fullDamageRange` (2.5 tiles), decaying to zero at `maxRange` (6.5) — the only weapon with one; every other ranged weapon leaves range entirely to the Cone of Fire's spread/falloff. That started life as a flat 3.5-tile cutoff, which enforced the identity but as a binary gate: full damage at 3.4 tiles and nothing whatever at 3.6. Telemetry showed it locked to the wrong band — regular enemies are fought at a median 4.6 tiles, outside its reach entirely, while the 10-15 HP Edge Case trash sits at 2.7. The decay keeps the short-reach identity honest (reach ends because damage becomes negligible, not because of an invisible wall) and pays for the extra range by starting the falloff *before* the old cutoff.

**Fire cadence is a third design axis**, alongside damage and ammo cost — and for a long time it silently wasn't one. Automatic weapons always had a `fireIntervalSec`, but the pistol and shotgun defined none at all, so their real rate was whatever a mouse hand could produce. That made "click faster" strictly better and let a 7-pellet shotgun be played as an automatic weapon, which is both unrealistic and the single most effective thing a player could do. Every ranged weapon now defines an interval. The Regex Shotgun's 0.85s pump is the one with real design weight: the pause *is* what the burst damage is paid for, and it's what keeps the shotgun and gdb from collapsing into the same weapon at different damage numbers.

The cap and the damage number have to be tuned as a pair, which is easy to miss. Capping the shotgun alone would have left it at 7×18/0.85s = 148 DPS against the pistol's 22/0.15s = 147 — identical output for **4× the ammo cost, out of what was then the same shared bullets pool**, and only at contact range where the whole cone connects. That erases every reason to pick it. Per-pellet damage went 18 → 25 in the same change for exactly that reason, restoring ~206 DPS (~1.4× the pistol). Anyone retuning either number should re-check the ratio, not just the cadence.

Two properties of the cap are deliberate. It lives on the *player*, not the weapon, so tapping `1` and back can't switch-cancel a pump. And quick-melee bypasses it entirely, so a player caught mid-cycle always has something to swing rather than standing helpless — the same safety-net role the knife plays for an empty ammo pool.

Loot rolls exclude outcomes that would be pointless in context: smg/rocket/gas ammo never drop before the matching weapon is unlocked, so a drop the player can't use at all doesn't happen — it would read as the game wasting their luck. Health used to be part of the same weighted roll (skipped only at full stability); it's now its own always-on check instead, independent of everything else — any regular kill tops the player up if they're not at full stability, no roll involved. That split happened after balance telemetry found cutting health the same way as ammo (see below) collapsed Hard's clearing rate: health is the one resource that directly ends a run when it runs short, unlike ammo, which stays survivable via the knife/Toolchain melee fallback. Ammo/armor still come from one weighted roll per kill, but that roll doesn't always land anymore — a 20% chance (`REGULAR_KILL_NO_DROP_CHANCE`) it drops nothing at all, added after the same telemetry found dynamic (kill-drop) supply so overwhelmingly dominated static level placement (93-100% of everything actually consumed, every resource type) that ammo never felt meaningfully scarce regardless of level design.

The SIGKILL Knife (melee, unlimited ammo, small lifesteal) exists as a deliberate safety net: since a kill's ammo/armor roll can now come up empty (and always could, before a weapon is unlocked, or once a pool runs dry between drops), the knife's job is to make sure a player who's fully dry can still fight their way back into the loop rather than getting stuck. Toolchain takes over that same job once found — a stronger chainsaw with double the damage and a bigger heal-per-kill, permanently replacing the knife on Space rather than sitting alongside it, and (unlike the knife) firing continuously while held instead of once per press. It doesn't remove the safety net, it just upgrades it for whoever gets lucky enough to find it. Toolchain itself gained a third way to get lucky: alongside the pre-existing secret-room and Elite-bonus-roll paths, a regular kill's ammo/armor roll coming up empty now carries its own small independent chance (5%) to grant Toolchain instead of nothing at all — added after balance telemetry found the other two paths were, in practice, close to unreachable (a shortest-path bot never explores for secret rooms at all, and an early clean Elite kill is rare).

## Scoring intent

Scoring is built to reward the behaviors the game actually wants to encourage, not just "kill things": points scale with the complexity of what was defeated (tripled for an Elite), plus bonuses for finishing with health/ammo to spare, for speed, and for route efficiency (actual path walked vs. the shortest possible spawn→exit path) — and a separate bonus for reading lore terminals, for opening secret rooms (double the lore bonus per room, since finding one takes actively interacting with a specific stretch of wall rather than just walking near a terminal), and for exploring most of the map, so pure speedrunning isn't the only path to a high score. Chaining kills fast also pays off directly: 3 kills within 3 seconds of each other triggers a "MULTI KILL!" bonus, and 6 within 6 seconds an "ULTRA KILL!" (bigger bonus, matching the top-tier map-completion bonus), each with its own on-screen banner and procedural stinger — a rolling-window check, so a long streak only announces once per tier crossed rather than spamming every subsequent kill. Score is a running **campaign total**, not a per-level number that resets — a multi-level run is meant to read as one continuous performance, not a sequence of disconnected level scores. (This was originally broken — see [Persistence & Storage Limits](decisions.md#persistence--storage-limits) — and fixed once identified.)

## Known design gaps

A few open items in [`notes`](../../notes)' `## Open` section are design-facing rather than pure engineering backlog, and are called out here so this doc doesn't read as though the design is finished:

- **Balancing** is explicitly still open — numbers throughout (HP curves, drop rates, aggro distances) are expected to keep moving.
- **Room decorations** were implemented once, disabled twice after playtest feedback (felt like visual clutter rather than atmosphere), and are sitting behind a flag pending a design rethink — not deleted, because the underlying idea (rooms feeling less empty) is still worth pursuing.

See `notes` directly for current status on any of these — this doc intentionally doesn't track checkbox state.
