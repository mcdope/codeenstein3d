# Architecture

Codeenstein 3D is built as four strictly-layered stages, each of which only knows about the plain-data contract the previous stage hands it:

```
fs  →  parser  →  map  →  engine
```

For the actual file listing, see the root [`README.md`](../../README.md)'s "Project Structure" section. This document covers the contracts and rules between layers, and why they exist — for *why a given rule was chosen over an alternative*, see [Design Decisions](decisions.md).

## `fs` — source acquisition

`src/fs/workspace.ts` (local, via the File System Access API), `src/fs/github.ts` (a public GitHub repo's tree + lazily-fetched raw file content), and `src/fs/demoCampaign.ts` (the bundled `demo-campaign/` showcase campaign, inlined into the app's own bundle at build time via `import.meta.glob` — no picker, no network) all produce the same `TreeNode` shape. Nothing downstream — file tree UI, entrypoint detection, level launching, replay — ever special-cases which one supplied a given file; a `TreeNode`'s `handle` is a union wide enough to cover a real `FileSystemFileHandle` and a minimal `RemoteFileHandle` (which the demo loader also uses, wrapping an already-in-memory string instead of a network fetch).

## `parser` — source → normalized AST data

`src/parser/types.ts` defines `ParsedFile` and states the rule directly in its own doc comment: *"This module defines the ONLY shape the rest of the engine is allowed to know about... Nothing outside `src/parser/` should import `web-tree-sitter`."* A `ParsedFile` is plain, serializable JSON: `language`, `linesOfCode`, `entities` (functions/methods/classes/globals, each with a `complexityScore` and `nestingDepth`), `gotos` (resolved `goto`/label pairs), `comments` (large comment blocks), `secretTriggers` (dead code, empty catch blocks, deprecation markers, commented-out code, and magic-number/blob literals — source for secret rooms), `exceptionZones` (`try`/`catch`/`finally` constructs) and `importCount` (top-level imports/includes/requires); each entity additionally carries an optional `switchBranches` summary and `allocations` count.

Dispatch is by file extension (`src/parser/registry.ts`), against a single shared Tree-sitter WASM bootstrap (`src/parser/runtime.ts`, `Parser.init()` memoized so it only runs once regardless of how many adapters need it). PHP and C get bespoke, hand-written adapters — their grammars have quirks (PHP's global-variable-at-program-scope detection, C's buried function declarator) a generic traversal can't capture precisely. The other 12 bundled languages share one data-driven `GenericParserAdapter` (`src/parser/generic/`), driven by a shared node-type vocabulary rather than 12 separate hand-written adapters — see [Dependency Minimalism](decisions.md#dependency-minimalism).

`src/parser/security.ts` sits ahead of every adapter: an extension whitelist (only extensions a registered adapter claims ever reach a parser), a 4 MiB size cap, and a binary-content sniff (non-printable byte ratio over a sample window). Its own doc comment is explicit about scope: *"Nothing in this file — or anywhere else in `src/parser/` — ever evaluates, compiles, or executes the text it inspects. Source text is only ever handed to `Parser.parse()` ... or plain string/regex scans."* A parse failure logs a warning and skips the file rather than crashing the map generator or game loop.

## `map` — AST data → level data

`src/map/mapGenerator.ts`'s `MapGenerator.generate(parsed: ParsedFile, ...)` turns a `ParsedFile` into a `GameMap` (`src/map/types.ts`): a tile grid plus `Enemy[]`, `Room[]`, hazards, doors, keys, teleporters, traps, and pickups. Like `ParsedFile`, a `GameMap` is plain, serializable data — nothing in it references the engine, the player, or the DOM. Generation is deterministic: a seed is derived from a hash of the parsed AST itself (`seedFrom()`), fed through the shared `mulberry32` PRNG (`src/prng.ts`), so the same source file always yields the same map.

`mapGenerator.ts` itself is only the orchestrator: every placement subsystem is a pure function module under `src/map/generation/` (`corridors`, `breakup`, `doorsKeys`, `enemies`, `props`, `pickups`, `lore`, `secretRooms`, `teleporters`, `trapsHazards`, `spawnExit`, `labyrinth`, `geometry`, `pathing`, `seed`, `util`, plus the four AST-driven features `switchboards`, `exceptionZones`, `vendorDepots`, `acidOverflow`), each taking the shared grid, accumulator arrays, and the seeded `rng` explicitly. `generate()` is the single place their ordering — and therefore the deterministic rng draw sequence — is defined; reordering calls there changes every existing map layout and desyncs every recorded replay.

One post-carve pass doesn't derive from the AST at all: `breakUpLongCorridors` scans the fully-carved grid for straight corridor runs past a length threshold and interrupts each one with a small injected room (or a forced jog if the room won't fit), tracked separately as `GameMap.breakupRooms: Rect[]` rather than folded into `Room[]` — it has no backing `CodeEntity`, so every AST-driven system stays untouched by construction rather than needing a guard clause. Its own "Edge Case" enemies (`Enemy.edgeCase`) are the one enemy type not derived from a parsed entity either — see [Corridor Breakup: Best-Effort, Not Guaranteed](decisions.md#corridor-breakup-best-effort-not-guaranteed). Every room being reachable from spawn, by contrast, *is* a hard invariant (`assertAllRoomsReachable` checks it at the end of every `generate()` call) — see [Room Connectivity Is a Hard Guarantee, Corridor Length Isn't](decisions.md#room-connectivity-is-a-hard-guarantee-corridor-length-isnt).

### "Enemy stays data"

`Enemy` (and similarly `Mine`, other trap types) is a bare interface — position, HP, cooldown timers, a `home` room rectangle, `aggroed`/`discovered` flags, a back-reference to the `CodeEntity` it represents — with **zero methods**. The doc comment on `Enemy.attackCooldown` states this directly: *"Behaviour lives in `src/engine/enemyAi.ts` — this stays plain data."* All actual behavior (roam/chase/melee/ranged state machine, line-of-sight, steering) lives in free functions in `src/engine/enemyAi.ts` that take the `Enemy[]` array, the `Player`, and the `GameMap`, and mutate the plain data in place. `enemyAi.ts`'s own header explains why: *"This lives in the engine layer rather than as a method on the `Enemy` data ... so the map never depends on the player."* The same split applies to traps (`src/engine/traps.ts` mutates plain `Mine`/`SpikeTrap` data on `GameMap`).

Practical effect: the map layer can be generated, seeded, and reasoned about — including in the replay system — with no dependency on player state, input, or rendering at all.

### Why `difficulty.ts` and `prng.ts` live at `src/` root

Both `src/difficulty.ts` and `src/prng.ts` are needed by more than one layer, and the map layer must never import the engine layer (the reverse is fine and expected). Rather than duplicate either module or force an awkward import direction, both live at `src/` root, outside `map/` and `engine/` entirely — layer-neutral by construction. In practice, difficulty scaling is applied by `engine.ts` (enemy HP is rescaled in-place on the map's `Enemy` objects right after construction) rather than threaded through `MapGenerator.generate()`, but the module itself stays usable from either layer.

## `engine` — level data → running game

`src/engine/` (38 modules) consumes a `GameMap` + a `Player` and runs the render/simulation loop, reporting `EngineStats` back to `main.ts` via `EngineHandlers` callbacks. Key modules: `engine.ts` (game loop), `raycaster.ts` (renderer), `textures.ts` (per-styleset `LevelStyle`s — wall/door/floor bitmaps, ceiling and automap colors: procedural defaults, or WAD-sourced via `src/wad/`), `player.ts`, `enemyAi.ts`, `pathField.ts` (one shared player-rooted BFS distance field all chasing enemies steer by, refloods only on player tile change or a grid mutation), `spatialGrid.ts` (tile-bucketed enemy index for rocket proximity/blast queries, rebuilt only on frames with rockets in flight), `sprites.ts`, `weapons.ts`, `ammo.ts` (the four ammo pools as one keyed record + per-pool metadata), `loot.ts` (drop rolls), `lootApply.ts` (drop/pickup application behind the narrow `LootContext`), `projectiles.ts`/`rockets.ts`, `traps.ts`, `acidOverflow.ts` (the runtime half of the Acid Overflow room event — see [Runtime Grid Mutation Safety](decisions.md#runtime-grid-mutation-safety) for why it deliberately never touches the reconciliation grid delta), `scoring.ts`, `highscores.ts`/`defaultHighscore.ts`, `replay.ts`, `audio.ts`/`bgm.ts`, `hud.ts`, `viewmodel.ts`, `automap.ts`, `effects.ts`, `input.ts`, `storageCompression.ts`, `perfDebug.ts` (opt-in `?perfDebug=1` per-frame phase-timing diagnostics), `playerStats.ts` (the dormant level-end stats screen, see [Feature Flags](#feature-flags)), `telemetry.ts` (balancing-bot tracking types/helpers, see [Balancing Telemetry Bot](balancing-telemetry.md)). Five more exist purely to back multiplayer (see the `multiplayer` section below) while staying in `engine/`, not `multiplayer/`, since what they gate is engine-layer simulation state, not session/transport concerns: `transitionConstants.ts` (the exit countdown), `reconciliationConstants.ts`/`reconciliationSnapshot.ts` (the periodic drift-correction pass), `lagCompensationConstants.ts` (rewinding hit-tests against a delayed enemy position), and `multiplayerScaling.ts` (Elite HP/damage scaling by player count).

### Rendering

Pure Canvas 2D — no WebGL, no 3D library. `raycaster.ts` casts one DDA (Digital Differential Analyzer) ray per screen column at a 640×400 internal resolution (CSS-scaled up for a chunky retro look), drawing one shaded vertical wall strip per column. Shading is distance fog plus a fixed y-side dimming for fake directional lighting. Walls, doors, the floor, lore-terminal walls, and hazard/teleporter/spike-trap floor tiles are all texture-mapped, organised into **stylesets**: one coherent look — wall, floor and door bitmaps plus a ceiling color and a minimap wall color — that a level keeps for its whole duration. `src/engine/textures.ts` owns a `LevelStyle` per `StyleSetId` (`stone`, `rust`, `tech`, `marble`, `techCool`); which one a level gets is decided in the map layer and carried on `GameMap.styleSet` (see [Per-Level Stylesets](decisions.md#per-level-stylesets)). Only the three *structural* slots vary between stylesets. The five *gameplay-signal* slots — lore-terminal wall, hazard floor, teleporter floor, spike-trap safe/active floor — are built once and shared by reference across every styleset, deliberately: "this tile will hurt me" must read identically on every level. Everything is generated by default as procedural patterns into detached offscreen canvases (brick, steel panel and bevelled-ashlar blockwork walls; flagstone, metal-grating and poured-concrete floors; one two-leaf door shape recolored per styleset) — keeping the "no external asset files" approach the rest of the engine already uses (`audio.ts`, `viewmodel.ts`) — or, if the player loads a DOOM WAD file via the sidebar, real composited wall/door/lore-terminal textures and floor/hazard/teleporter/spike-trap flats parsed out of it by `src/wad/` (a from-scratch WAD/PLAYPAL/TEXTUREx/patch/flat binary parser — deliberately hand-rolled rather than an npm dependency, see [Dependency Minimalism](decisions.md#dependency-minimalism)), auto-selected from a hardcoded name allowlist that is itself grouped per styleset (the full slot/name table, the format constraints a pack has to meet, and how to check one are in [WAD Texture Packs](wad-texture-packs.md)). A structural slot with no match in that styleset's own list falls through to the *other* stylesets' candidates for the same slot before dropping to the procedural default, so a sparse WAD degrades to "two stylesets look alike" rather than "some levels are WAD-textured and others aren't" (see [Per-Level Stylesets](decisions.md#per-level-stylesets)). The renderer samples per-column via `drawImage` plus a shading overlay for walls/doors/lore-terminals, and per-pixel during the floor-cast for the floor/hazard/teleporter/spike-trap tiles. The ceiling is the only thing left deliberately *not* textured, staying flat-colored — in the styleset's own ceiling tone. Secret walls reuse the plain wall texture plus a subtle identifying tint overlay rather than getting their own slot (they must stay near-visually-identical to a plain wall); lore-terminal walls get their own real texture plus a much more visible pulsing tint overlay on top, since — unlike secret walls — they want to be noticed as interactive, and that pulse used to be their entire "this is a terminal" signal before texturing. Spike traps swap between two different WAD flats (a plain/metal one and a blood/lava one) depending on whether `activeSpikeTileKeys` says the trap is in its safe or damaging phase, rather than tinting one texture — the real signal a player needs, modeled as which flat is showing instead of a color. Hazard and teleporter floor tiles sample their real WAD flat with no tint at all, matching how Doom itself renders these; the JS-computed sine-wave pulse they used to have before texturing is gone (real Doom animates these via multi-frame flat-cycling, which this engine doesn't implement). Each column's wall top/bottom edge is kept as a float rather than floored to a whole pixel, and the one boundary row at each edge is alpha-blended (sampling the exact texel color for textured columns) against whatever's already painted underneath in proportion to its sub-pixel coverage — antialiasing the top/bottom silhouette against ceiling/floor without touching the `zBuffer` (still one exact distance per column, so billboard occlusion is unaffected). Vertical seams between adjacent columns (e.g. at corners) are not antialiased — that would need supersampling across columns, which is a bigger cost/architecture change (`notes` Task 71).

`src/wad/` is its own small acquisition layer, structurally analogous to `parser/`: plain byte-array-in/plain-data-out, with zero DOM/Canvas dependency (fully testable in plain Node — `scripts/verify-wad-parser.mjs`), and consumed only by `src/engine/textures.ts` — nothing else in the engine, and nothing in `map/`, ever needs to know the WAD binary format. It sits outside the `fs → parser → map → engine` pipeline proper: it's user-triggered at any time via the sidebar (not part of a level's fs/parser/map derivation), session-only (not persisted, matching the existing "Select BGM Folder" precedent), and never affects simulation/replay determinism — texture choice is purely cosmetic.

Besides a local `.wad` file, the sidebar also offers a curated **online WAD catalog** (`src/wad/onlineWadCatalog.ts`) that feeds the exact same `textures.loadFromWad`/`loadWadTextures` path — from the engine's point of view it's just another `ArrayBuffer`, sourced via a same-origin `fetch("/wads/<file>.wad")` instead of `<input type="file">`. None of the catalog's original upstream hosts send CORS headers a browser fetch could use, so the actual acquisition happens outside the runtime app entirely: `scripts/fetch-online-wads.mjs` (Node-only, run via the `predev`/`prebuild` npm hooks, idempotent — skips any file already present locally) downloads each source (a ZIP to extract from, or a raw `.wad` served directly), extracting via a small hand-rolled ZIP reader when needed (`scripts/lib/zipReader.mjs`, see [Dependency Minimalism](decisions.md#dependency-minimalism)), and writes the result into `public/wads/` — Vite's default static-asset directory, served as-is, gitignored rather than committed since these are large (tens of MB each) third-party game-data files re-fetched per machine/CI run rather than checked into source control. Every entry is round-tripped through `loadWadTextures` at fetch time and must resolve most/all of the 20 texture slots (3 structural x 5 stylesets, plus the 5 shared signal slots) — `npm run report:wad-stylesets` prints the full styleset x slot matrix plus a per-candidate decode probe for every WAD in `public/wads/`, which is how `textureAllowlist.ts`'s "every name decodes against a real WAD" bar is checked whenever that file changes — a WAD from a different game engine, or a texture-only resource patch with its own non-classic lump names, doesn't belong in the catalog even if its license is fine (see `onlineWadCatalog.ts`'s own doc comment for two rejected candidates).

Enemies and items are 2D billboards (`sprites.ts`), projected with the same camera transform as walls. Every world billboard — enemies, projectiles, keys, ammo drops, the exit marker, teleporters, mines — is collected into one list and drawn in a single furthest-to-nearest depth-sorted pass against a per-column `zBuffer` recorded during the wall pass, so occlusion (by walls or by other billboards) is always correct regardless of draw-call order. This replaced an earlier fixed-order-by-category approach that could draw a nearer item behind a farther one — see [Feature Scope Reversals](decisions.md#feature-scope-reversals).

### Determinism and replay

Anything that affects simulation outcome — enemy AI roam/fire-cooldown timing, loot rolls, weapon cone-of-fire spread, elite-loot coinflips — draws from the shared seeded `mulberry32` PRNG (`src/prng.ts`), never `Math.random()`. Purely cosmetic randomness (blood-particle scatter, SFX pitch, BGM shuffle order, console hint selection) stays on `Math.random()` deliberately, since it never feeds back into simulation state. This split is a hard constraint, not a style preference: the replay system (`replay.ts`) records a gameplay seed plus a per-frame input digest per level, and can only reconstruct a byte-identical run if every simulation-relevant random draw goes through the one deterministic stream. See [Determinism & Replay](decisions.md#determinism--replay) for how this evolved. This same determinism is exactly what multiplayer's own lockstep model (below) leans on: every peer's `RaycasterEngine` independently replays the identical seeded draw sequence from the identical input sequence, rather than one peer's simulation state ever being transmitted wholesale.

## `multiplayer` — real-time coop, layered on top of `engine`

`src/multiplayer/` (26 modules) never modifies `fs`/`parser`/`map`/`engine` — it wraps a real `RaycasterEngine` per peer (host and each guest independently construct and run their own, via `sessionEngine.ts`'s shared `buildSessionEngine()`) and drives it externally (`RaycasterEngine.startExternallyDriven()` + `advance(FIXED_DT)`, not the engine's own internal `requestAnimationFrame` loop) from a real per-tick `Worker` clock (`tickClockWorker.ts`) instead of a real per-frame one. `multiplayerSessionHost.ts`/`multiplayerSessionGuest.ts` are the two session drivers (host-authoritative broadcast vs. guest apply-and-reconcile), `signalingClient.ts`/`webrtcConnection.ts` handle the WebRTC handshake against `scripts/multiplayer-server.mjs`'s signaling server, `sessionSetupHost.ts`/`sessionSetupGuest.ts` handle the initial map/carryover handoff (and every later level transition's), `inputDelayBuffer.ts`/`networkInputSource.ts`/`localInputSampler.ts` implement the lockstep input-delay pipeline, and `reconciliationSnapshot`/`reconciliationConstants` (in `src/engine/`, not here — reconciliation itself is an engine-layer concern the multiplayer layer only triggers) back the periodic drift-correction pass. Full design/wire-protocol/topology detail lives in the three dedicated specs, not duplicated here: [`multiplayer-netcode-spec.md`](multiplayer-netcode-spec.md) (lockstep/reconciliation/session-lifecycle design), [`multiplayer-game-state-spec.md`](multiplayer-game-state-spec.md) (per-player state, spawns, Elite scaling), and [`multiplayer-server-spec.md`](multiplayer-server-spec.md) (the signaling server's own HTTP/rate-limit contract) — plus [`multiplayer-deployment.md`](multiplayer-deployment.md) for standing up a real signaling server.

## Build

Vanilla TypeScript + Vite 8, strict `tsc`, no game framework. `vite.config.ts` aliases `fs/promises`/`module` to `src/empty-node-shim.ts`, an empty stub — purely to satisfy Rollup's static resolution of `web-tree-sitter`'s bundle, which references a Node-only code path that's dead in a real browser but still needs to resolve at build time.

Unit coverage is a Vitest suite (`src/**/*.test.ts`, co-located next to what they test) with a ~99.9%-lines/statements/functions/branches gate (`npm run coverage`), wired as a blocking CI job alongside the browser-driven scripts below — see [Testing](testing.md) for the full setup, shared mock catalog, and mocking philosophy; broad gameplay/visual e2e coverage beyond the scripts here remains an open backlog item in `notes`. There are 14 `scripts/verify-*.mjs` scripts in total, split across CI by whether they need a real browser and — for the genuinely slow multiplayer ones — whether they get their own dedicated job so their wall-clock cost runs concurrently with everything else instead of stacking onto a shared leg. `scripts/verify-wad-parser.mjs`, `scripts/verify-zip-reader.mjs`, `scripts/verify-demo-campaign.mjs` (see `notes` Task 76), and `scripts/verify-multiplayer-server.mjs` are pure Node — the third of those bundles the real parser + `MapGenerator` via esbuild (no browser needed) and gates on a full map-feature/enemy-type coverage checklist (including one item per AST-driven feature: Switchboard spur, Exception Handling Zone, Vendor Depot, smg/gas depot stock, and Acid Overflow room), and the fourth spawns `scripts/multiplayer-server.mjs` itself as a child process and drives its HTTP endpoints with plain `fetch()` (see `doc/dev/multiplayer-server-spec.md`) — and all four run in the `verify` (no-browser) CI job; `scripts/verify-wad-textures.mjs`, `scripts/verify-campaign-playthrough.mjs`, `scripts/verify-multiplayer-connect.mjs`, `scripts/verify-multiplayer-netcode.mjs`, `scripts/verify-multiplayer-reconciliation.mjs`, and `scripts/verify-multiplayer-disconnect.mjs` are genuinely Playwright-driven, each spinning up a real headless browser (or two, for the multiplayer ones) against a real dev server, and run in the shared `verify-browser` job — as a `chromium`/`firefox`/`webkit` matrix (see [Testing](testing.md#cross-browser-verification) for why the scripts that run on all three are safe to run against a non-Chromium engine, and which multiplayer scripts skip which engine and why). `scripts/verify-multiplayer-transition.mjs`, `scripts/verify-multiplayer-multiguest.mjs`, and `scripts/verify-multiplayer-determinism.mjs` (cross-browser determinism, `verify-determinism` job) are each split into their own dedicated CI job — real, multi-minute multiplayer sessions, chromium-only (see [Testing](testing.md#cross-browser-verification) for the webkit-timing/Firefox-ICE reasoning behind each skip). `scripts/verify-multiplayer-campaign.mjs` is the one verify script deliberately **not** CI-wired at all — an uncapped, potentially-full-real-campaign-length run has no bounded worst-case wall-clock cost (see [Testing](testing.md#cross-browser-verification)); run manually. `verify-campaign-playthrough.mjs` drives the real app end-to-end (via an OPFS-stubbed workspace picker and a virtual clock) to verify the save/highscore/replay mechanism; `verify-wad-textures.mjs` loads a synthetic in-memory WAD and confirms wall/door/floor/lore-terminal/hazard/teleporter/spike-trap texturing actually reaches the live renderer, saving a screenshot for manual spot-checking of anything not worth a hard pixel assertion; `verify-multiplayer-connect.mjs` drives two genuinely separate Playwright browser **contexts** (not just tabs — each needs its own real `RTCPeerConnection` stack) through the real Host/Join UI and confirms both reach an open `RTCDataChannel` — proving `multiplayer-research.md`'s implementation-plan step 2 (see `doc/dev/multiplayer-netcode-spec.md`), and the one place a real WebRTC ordering bug (not catchable by any mock-based unit test) was actually found while building it. Both `scripts/generate-default-highscore.mjs` and `scripts/run-balancing-telemetry.mjs` drive the game through the same shared `Bot` class (`scripts/lib/bot.mjs`) — real navigation (`scripts/lib/routePlanner.mjs`, on top of `pathfind.mjs`'s BFS) and combat (turns toward/fires at nearby enemies — those already aggroed, plus, for the profiles that opt in, ones inside the engine's own aggro radius with line of sight and a short *walking* distance, which would have noticed the player unprompted anyway — via the undocumented `Backquote` automation-only fire key — see `isFireHeld()`'s doc comment in `src/engine/input.ts` — no mouse/Pointer Lock needed), each configured via explicit constructor options rather than reading `process.env` itself; the multiplayer verify/telemetry scripts reuse the same `Bot` class through a thin `MultiplayerBot` subclass (`scripts/lib/multiplayerBot.mjs`). `scripts/lib/qualifyLoop.mjs` holds the retry-until-N-qualifying-runs loop both scripts use; `scripts/lib/virtualClock.mjs` holds the virtual-clock installer both share. The bot's *decision* logic lives in `scripts/lib/combatPolicy.mjs` — `decide(world, memory, config)` returns an intent (which keys to hold and for how long, whether to fire, which weapon to switch to) and `bot.mjs` is the I/O half that dispatches it, with `dispatchSegment` as the single page-touching method `MultiplayerBot` overrides. That module is deliberately written to be liftable into `src/engine/combatPolicy.ts` later, as the basis of a real in-game deathmatch opponent: `src/` can't import from `scripts/`, so the move has to be a copy, and its doc comment lists the rules that keep such a copy mechanical (no page, no async, no Node builtins, all tuning injected, no `Math.random`/`Date.now`, total sorts). It reads in-flight enemy bolts through `getProjectiles` to step off their flight lines rather than only reacting to damage already taken. `scripts/lib/` now carries real unit coverage of its own — `combatPolicy.test.mjs`, `anomalyDetectors.test.mjs`, `routePlanner.test.mjs`, `abReport.test.mjs` and `laneOrchestrator.test.mjs`, alongside `scripts/multiplayer-server.test.mjs` — since `scripts/**` is excluded from the `src/` coverage denominator but still executed by `vitest run`, so all of them run in CI (see [Testing](testing.md#unit-tests-under-scripts--outside-the-coverage-gate-still-run-by-ci)).

`scripts/generate-default-highscore.mjs` (`npm run generate:default-highscore`, `notes`) is a one-shot dev tool, not a verifier: for each bot skill profile (Casual/Gamer/Pro), it plays `demo-campaign/` until 3 runs qualify (reach campaign level 4/5/6 respectively), keeps the single highest-scoring qualifying run per profile, and bakes the resulting 3 entries into `src/engine/defaultHighscore.ts` — the shipped fallback leaderboard shown to a first-time player with an empty highscore board. The file is a single encoded string constant (`bin1:` prefix — binary frame packing via `replayCodec.ts`, then gzip and base64, the same encoding `localStorage` gets), not a plain array literal — a qualifying run's replay can carry tens of thousands of frames, and both the shipped bundle size and the cost of a bundler parsing the data mattered enough to compress it (an early uncompressed version of this file reached ~84MB). It is emitted as its own lazily-imported chunk, so it costs a first-time visitor nothing until they actually open an empty Highscores dialog. `loadHighscoresForDisplay` (`highscores.ts`) decodes it on demand via `readBoard`, which also still accepts the older `gz1:` and bare-JSON forms. Rerun the generator (and review the diff) whenever `demo-campaign/`'s source files change, or its baked-in replay `astHash` values go stale and playback refuses.

**Rerun it after a balance change too, not only a source change.** A replay is a raw input stream replayed against a freshly built engine, and `astHash` covers *"parsed AST JSON + campaign name"* — it answers "is this still the same source file", not "is this still the same game". Enemy HP is generated *from* the AST rather than being part of it, so halving `ELITE_HP_MULTIPLIER` left every `astHash` matching while making every affected replay diverge silently, showing a run that no longer matches its own score. `src/engine/balanceHash.ts` closes that: each segment records a `balanceHash` over the generated enemy roster plus `SIMULATION_BALANCE` (the engine-side constants), checked at playback right after `buildEngineFor`. A mismatch ends the replay with a clear message instead of playing a lie.

Two deliberate limits worth knowing before extending it. It hashes the enemy **roster**, not the whole map: the generator's weapon-ownership options leave enemies byte-identical but change `ammoPickups` and the grid, and those options are *not* stable between recording and playback, because `main.ts` generates the map from `carryover` while the segment stores `effectiveCarryover` (which force-adds weapons at campaign levels 4/8/12). Hashing pickups or layout would therefore refuse perfectly good replays. And a **missing** `balanceHash` is accepted rather than refused, so runs recorded before the guard existed — including the currently-shipped `defaultHighscore.ts` entries — keep working; they get the old behaviour, and everything recorded from here on is checked.

`scripts/run-balancing-telemetry.mjs` (`npm run balancing:telemetry`, `notes` "balancing") is a third headless-Chromium bot script, built for data collection rather than shipping an artifact: it plays `demo-campaign/` with three bot profiles (Casual/Gamer/Pro, defined in `scripts/lib/profiles.mjs` and re-exported from `scripts/run-balancing-telemetry.mjs`) across all three difficulties, retrying each of the 9 profile×difficulty combos until it collects 3 "qualifying" runs (a run qualifies once it clears level 4 — earlier deaths are discarded outright), and writes a self-describing 7-category telemetry breakdown (map density/enemy demographics, combat pacing/TTK, AI effectiveness, damage/healing, weapon efficiency, economy/loot, navigation) per level and per campaign to `balancing_telemetry.json` at the repo root (gitignored — regenerate on demand, not a build artifact). All runtime data comes through dedicated additions to `window.__codeensteinTestHooks` — `getMines()` and `getTelemetrySnapshot()` — backed by pure tracking types/helpers in `src/engine/telemetry.ts` and `RaycasterEngine`'s `?testHooks=1`-gated instrumentation (also the gate for `PLAYER_STATS_ENABLED`'s player-facing stats screen — see [Feature Flags](#feature-flags)); nothing here uses a fresh `Math.random()` call — bot decisions stay deterministic via the engine's existing seeded `mulberry32` streams (note: the top-level *gameplay seed* itself is still randomized fresh per process launch, so two separate invocations of the same script at identical settings are not expected to produce byte-identical output). Each combo's attempts run concurrently (`ATTEMPT_CONCURRENCY`, default 12, `CODEENSTEIN_TELEMETRY_CONCURRENCY` env override) via isolated Playwright browser contexts sharing one Chromium process; a single flaky context crashing (`page.evaluate: Target page, context or browser has been closed`, observed intermittently under concurrency) is caught per-attempt and discarded rather than taking down the whole run, with a circuit breaker if the browser itself appears to have died. A full 9-combo run is a long, mostly-unattended job (tens of minutes to a few hours depending on how many attempts each combo needs) — see `CODEENSTEIN_TELEMETRY_HEADED=1` for watching one attempt play in a real (non-headless) browser at human-readable speed when diagnosing bot behavior, and `CODEENSTEIN_TELEMETRY_LEVEL_LIMIT`/`CODEENSTEIN_TELEMETRY_ATTEMPT_CAP`/`CODEENSTEIN_TELEMETRY_PROFILE`/`CODEENSTEIN_TELEMETRY_DIFFICULTY` for scoping a smoke test down. See [Balancing Telemetry Bot](balancing-telemetry.md) for the full operational reference — every env var, the permanent `npm run balancing:scan` regression detector, and a critical headed-vs-headless timing gotcha (a convergence check tight enough to work perfectly under the virtual clock can be structurally unreachable in a real, visibly-rendered browser).

## Feature Flags

Hardcoded `export const X_ENABLED = <bool>` constants — no build config or env var, flip the source and rebuild. All default to whatever's actually shipping.

| Flag | Default | File | What it gates |
|---|---|---|---|
| `DECORATIONS_ENABLED` | `false` | `src/map/generation/props.ts` | Billboard room decor (racks/plants/desks) — disabled because billboarding reads as visibly wrong on boxy shapes; needs a non-billboard rendering approach to re-enable (`notes`). |
| `PLAYER_STATS_ENABLED` | `false` | `src/engine/playerStats.ts` | The level-end/run-end player-facing stats screen (kills, accuracy, damage taken, etc. — `GameHud`'s Commit Summary/Kernel Panic/Build Successful rows). Off because recording `telemetry.ts` on every real playthrough measurably slows gameplay, even with the derived stats gated to only compute at level-end — see the flag's own doc comment. `?testHooks=1` (the balancing bot) always gets telemetry regardless of this flag. |
| `WALL_EDGE_ANTIALIASING_ENABLED` | `true` | `src/engine/raycaster.ts` | Sub-pixel blending of the top/bottom wall silhouette against ceiling/floor, smoothing the raycaster's classic "staircase" jaggies. On by default since the 2026-07 perf audit measured the cost: below the 0.2ms/frame detection floor on demo-scale maps, ~+0.4ms on a 160×160 monster map (`npm run perf:bench -- --flag aa`). Threaded as `renderScene`'s `antialiasing` parameter (defaulting to this flag) rather than read directly, so a caller/test can override it without a rebuild. |
| `RESPONSIVE_CANVAS_SCALING_ENABLED` | `true` | `src/ui/canvasFit.ts` | Windowed-mode canvas resizing to fill available space (a `ResizeObserver` + `fullscreenchange` listener recomputing inline `width`/`height` on every resize) instead of a fixed max size. On by default since the 2026-07 perf audit: zero engine-side cost headless AND an attended on-screen headed A/B showed identical frame distributions — the compositor upscale is free (`npm run perf:bench -- --flag scaling`). `main.ts` checks the flag itself (not `canvasFit.ts` internally — see the module's own doc comment for why that split matters for testability). Fullscreen is unaffected either way (separate CSS rule). |
| `SWITCHBOARDS_ENABLED` | `true` | `src/map/generation/switchboards.ts` | The `switch`/`match` → junction-hub-with-case-spurs feature. Checked at the `mapGenerator.ts` call site, not inside the module, so a disabled feature draws **zero** rng and leaves every other placement's draw sequence (and therefore every existing map layout) untouched — same for the three flags below. |
| `EXCEPTION_ZONES_ENABLED` | `true` | `src/map/generation/exceptionZones.ts` | The `try`/`catch`/`finally` → acid-gauntlet/restoration-alcove/loot-room zone. |
| `VENDOR_DEPOTS_ENABLED` | `true` | `src/map/generation/vendorDepots.ts` | The imports → spawn-room supply-alcove feature. |
| `ACID_OVERFLOW_ENABLED` | `true` | `src/map/generation/acidOverflow.ts` | The allocation-density → room-floods-until-you-kill-it event. Gates only the generation-time *planning* pass; with no rooms planned, the engine-side runtime pass (`src/engine/acidOverflow.ts`) has nothing to iterate. |
| `DISTANCE_FOG_ENABLED` | `true` | `src/engine/raycaster.ts` | The distance fog ("farther = darker"): per-column black overlay `fillRect` plus the floor caster's per-scanline/per-pixel shading. Exists to *measure*, not to ship off — the 2026-07 perf audit's A/B found fog costs under 0.1ms/frame (below the harness's detection floor) even on a 160×160 map, so it stays on. Threaded as `renderScene`'s `fog` parameter, same pattern as `antialiasing` above. |

Benchmarking these: `npm run perf:bench -- --flag aa|scaling|fog --scenario s1-idle,...` runs an interleaved A/B with the flag temporarily flipped in-source (guarded restore); see `scripts/run-perf-benchmark.mjs`'s header and `npm run perf:report` for the chart report.
