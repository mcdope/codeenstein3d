# Code review — 2026-08-03

Four-axis read-only review (reuse/dedup, comments-vs-code, maintainability, performance).

**Scope**: `src/**` non-test (34.5k LOC), `scripts/**` (21.9k LOC), `index.html` + `src/style.css`
(1.4k LOC). The Vitest suite (34.7k LOC) was out of scope by agreement.

**Axis 4(a) — the per-frame render path — was taken as given.**
[`perf-review-2026-08-02.md`](perf-review-2026-08-02.md) audited it exhaustively on the reference
machine yesterday with real measurements. Nothing here re-derives it; the perf pass went to 4(b)
generation/repo-analysis complexity and 4(c) load path, which that audit did not cover.

**A note on what this review had to work against.** `doc/dev/` is unusually complete — `decisions.md`
records a dozen things that *look* like defects and are deliberate, down to per-combo A/B numbers.
The dominant failure mode for a review here is the false positive, so every finding below was
verified against source twice and cross-checked against `decisions.md`, `architecture.md`,
`testing.md` and the perf review before it was allowed to stand. §3 records what was checked and
deliberately *not* flagged, so the next pass doesn't re-derive it.

## 1. Summary — what I would fix first

1. **The `[hidden]`/`display` CSS trap has a live fourth instance.** `.multiplayer-code-wrap`
   sets `display: flex` with no `[hidden]` override, so `#multiplayer-host-code-wrap` — which ships
   with `hidden` and is toggled four times in `main.ts` — is visible whenever the Multiplayer→Host
   sub-tab is. `decisions.md` documents this exact class as having shipped three times already and
   as structurally invisible to the test suite. **Critical, one line to fix.**
2. **A race-condition fix reached five of six copies of `makeEligible`.**
   `verify-multiplayer-connect.mjs` is the copy that missed it — and it is a blocking CI job on two
   browser legs. This is the drifted duplicate the brief asks to prioritise.
3. **A second script drift, same shape**: `sampleFps`'s `.catch(() => null)` guard exists only in
   the telemetry copy, not in `verify-multiplayer-multiguest.mjs` — which is precisely the script
   that tears down contexts concurrently.
4. **`Enemy.elite`'s doc comment still promises 4x HP; the constant has been 2 since 2026-07-30.**
   `map/types.ts` is the data contract for the map layer, and this is the one number in it a reader
   is most likely to trust without checking.
5. **Fix the root cause behind (2) and (3)**: five verify scripts carry private copies of four
   helpers that already exist in `scripts/lib/multiplayerSessionBootstrap.mjs`, which three other
   scripts import. The shared copy is strictly the most evolved one.
6. **`placeSecretRooms` bypasses the helper that was extracted from it.** `geometry.ts`'s own doc
   comment names `placeSecretRooms` as the reference implementation for `sideCandidateFits` — but
   `secretRooms.ts` never migrated, so there are two exact copies of the fit rule and three other
   carvers depend on only one of them.
7. **Campaign autosave leaks on remote workspaces.** `workspaceIsRemote`'s doc comment says autosave
   is "skipped entirely" so a dead "Continue Run" button can't appear — but only the *throttled*
   save honours that guard. `advanceToNextLevel` writes directly on every level transition, so
   playing the Demos campaign and reloading produces exactly the dead button the design prevents.
8. **Small-but-cheap hygiene**: `clamp` defined five times byte-identical (`clamp01` twice) while
   `generation/util.ts` exists for it, and two memory-system wiki-links (`[[codeenstein-project]]`,
   `difficulty.ts:8` and `astUtils.ts:35`) citing a document that isn't in this repo.
9. **Level generation does up to 12 full-grid rescans and one full-grid BFS per door.** Free on the
   demo campaign (55–64 tiles); the honest answer for a 160×160 map is that it needs measuring, and
   §2.4 proposes the measurement rather than guessing.
10. `main.ts` (129 module-level bindings, 65 DOM handles) and `RaycasterEngine` (137 fields,
    `simulate()` at 326 lines) are the two god objects — with a concrete seam proposed for each
    rather than a "these are big" complaint.

## 2. Findings

### 2.1 Critical

#### C1 — `.multiplayer-code-wrap` defeats its own `hidden` attribute

`src/style.css:233`
```css
.multiplayer-code-wrap {
  display: flex;
```
`index.html:160`
```html
<div id="multiplayer-host-code-wrap" class="multiplayer-code-wrap" hidden>
```
`src/main.ts:1102, 1236, 1546` set `multiplayerHostCodeWrap.hidden = true`; `main.ts:1282` sets it
`false`.

There is no `.multiplayer-code-wrap[hidden] { display: none; }` anywhere in `src/style.css`
(the file has exactly three such overrides: `.tab-panel`, `.loading-screen`, `.canvas-area`).

**Why it's a problem.** `decisions.md`'s *UI/DOM Gotchas* states the rule directly: `[hidden]` works
only because of a *user-agent origin* rule, and any author-origin `display` declaration beats it —
"the element stays visible with `hidden` set, with no error and nothing in the console to hint at
it." So the session-code row (an empty `<p id="multiplayer-host-code">` plus a "Copy" button) is
painted as soon as the Multiplayer→Host sub-tab is shown, before any session exists, and the three
`hidden = true` calls are no-ops — a stale code stays on screen after cancel/leave. The `Copy`
button copies an empty string in that state.

Scope is bounded by an ancestor: `#tab-panel-multiplayer` is a `.tab-panel`, which *does* have the
override, so nothing leaks while another tab is selected. The defect is confined to the Host
sub-tab — but that is the entire host-side entry point for multiplayer.

`decisions.md` also explains why no test caught it: "jsdom applies no UA stylesheet, so a unit test
asserting `el.hidden === true` passes while the real browser still paints the element."

**Fix** — one line, matching the two existing precedents at `style.css:799` and `:854`:
```css
.multiplayer-code-wrap[hidden] { display: none; }
```
**Effort: S. Risk of the fix: none** — it can only ever hide an element that already carries
`hidden`.

Worth considering alongside it: the other `hidden`-toggled elements were all checked and are clean
(`.settings-btn`, `.muted`, `.tree-list`, `.replay-btn` set no `display`). A lint rule or a single
`[hidden] { display: none !important; }` reset would close the class rather than the instance —
this is now the fourth occurrence.

### 2.2 High

#### H1 — `makeEligible` drifted: the connect verifier never got the canvas-ready wait

Six copies exist. Five end with the same call; one does not.

`scripts/verify-multiplayer-netcode.mjs:63-82` (and `-disconnect.mjs:69-88`, `-transition.mjs:127-147`):
```js
  // The demo campaign's own level finishes auto-launching slightly after the
  // Multiplayer tab enables — the host's own `startMultiplayerSessionAsHost`
  // guard needs `currentParsedFile`/`currentLevelPath` to already be set.
  await page.waitForSelector(".canvas-area:not([hidden])", { timeout: 20_000 });
```
`-reconciliation.mjs:67-82` and `lib/multiplayerSessionBootstrap.mjs:73` have the same call without
the comment.

`scripts/verify-multiplayer-connect.mjs:106-119` — the complete function, ending at the tab check:
```js
  await page.waitForFunction(
    () => {
      const tab = document.querySelector("#tab-multiplayer");
      return tab instanceof HTMLButtonElement && !tab.disabled;
    },
    undefined,
    { timeout: 20_000 },
  );
}
```

**Why it's a problem.** The comment in the other copies states the race precisely: the Multiplayer
tab enables *before* `currentParsedFile`/`currentLevelPath` are set, and
`startMultiplayerSessionAsHost` guards on them. `verify-multiplayer-connect.mjs` therefore proceeds
to the host flow in a window where the guard can still reject. It runs as a blocking CI step on the
chromium and webkit legs of `verify-browser`. A failure here presents as a WebRTC/connect problem —
the least likely place anyone would look for a level-load race — and `testing.md` already documents
how much time that misattribution costs on this project.

**Fix**: import from the shared helper (see M1), or as a one-line stopgap append the same
`waitForSelector` call. **Effort: S. Risk: none** — it only adds a wait to a script that currently
proceeds early.

`scripts/verify-multiplayer-multiguest.mjs:106-121` is otherwise the same function body, with no

**Fix**: append the same `.catch(() => null)`, or share the helper. **Effort: S. Risk: none** —
callers already have to tolerate a numeric or absent sample.

#### M2 — `placeSecretRooms` bypasses the helper extracted from it

`src/map/generation/geometry.ts:295-297`, `sideCandidates`' own doc comment:
> Extracted from `placeSecretRooms`' original inline enumeration, which is still the reference for
> what "fits" means

But `src/map/generation/secretRooms.ts:113-198` (`trySecretRoomOffAnchor`) still contains that
inline enumeration and its own fit test. I checked the two against each other arm by arm — for a
square footprint at `offset` 0 they are **arithmetically identical** on all four sides (top:
`y0 = anchor.y - 1 - size` both sides; bottom, left, right likewise), and the fit test matches
`sideCandidateFits` exactly: same wall-is-rock check, same border bounds, same footprint-plus-1-tile
margin loop.

Meanwhile `switchboards.ts:116/124`, `exceptionZones.ts:121/126` and `vendorDepots.ts:89/92` all use
the shared helper.

**Why it's a problem.** Four carvers depend on one rule that is written down twice, and the copy the
doc names as authoritative is the one that isn't shared. A future correction to `sideCandidateFits`
— the margin rule is subtle, and its own comment explains it exists to stop two secret rooms
revealing each other — would silently miss the one carver the margin rule was invented for.

**Fix**: replace the inline enumeration with
`sideCandidates(anchor, SECRET_ROOM_SIZE, SECRET_ROOM_SIZE, 0)` + `sideCandidateFits(c, grid, mapSize)`,
keeping the existing `shuffle`-then-first-fit and the `SECRET_WALL_TILE` carve (which is genuinely
secret-room-specific and stays). No new parameters needed.
**Effort: S. Risk: MEDIUM and this is the important part** — `shuffle(candidates, rng)` consumes rng
in candidate-array order, and `sideCandidates` emits in a different order than the inline loop
(interleaved top/bottom then left/right vs. the same, but built with different index arithmetic).
Any change to the array's *length or order* moves every subsequent draw and therefore every existing
map layout, every recorded replay, and the shipped `defaultHighscore.ts`. Verify with
`mapGenerator.test.ts`'s exactness gate and `npm run report:level-maps` before/after; if the order
differs at all, this is not worth doing.

#### M6 — `renderMinimap` takes 11 positional parameters, `renderScene` 10

`src/engine/raycaster.ts:669-700`: `(ctx, map, player, levelTime, maxPixels, readTerminals,
gridVersion, lootDrops, runtimeAcidTiles, automapWall, pingedKey)` — eight of them optional with
defaults. `renderScene` (`raycaster.ts:229-240`) has ten on the same pattern.

**Why it's a problem.** Six consecutive optional parameters mean a caller wanting only the last must
spell out five defaults correctly, and two adjacent readonly-array parameters (`lootDrops`,

**This project has already made exactly this call and written down why.**
`src/map/mapGenerator.ts:71-77`, on `GenerateOptions`:

**Fix**: same conversion — keep `(ctx, map, player)` positional and move the rest to a
`MinimapOptions`/`SceneOptions` object. **Effort: M** (call sites in `engine.ts` plus tests).
**Risk: low** — render-side only, no simulation or draw-order change, and the precedent above
confirms the conversion is value-preserving.

#### M8 — `main.ts` is the application's global state as well as its entry point

`src/main.ts`, 3969 lines: **129 module-level `const`/`let` bindings**, **65 `requireElement()` DOM
handles at module scope**, 71 top-level functions. The two longest:

- `startReplay` — `main.ts:3420-3861`, ~442 lines. Workspace re-fetch (GitHub *or* local), engine
  reconstruction from a recorded segment, MediaRecorder setup/teardown, the rAF playback loop, and
  the replay-transport DOM wiring, in one body.
- `launchLevel` — `main.ts:2415-2637`, 223 lines. Forced-unlock carryover, map generation,
  multiplayer teardown, DOM viewport rebuild, HUD construction, replay recorder, engine construction
  with inline `EngineHandlers`.

**Why it's a problem.** Every one of those 129 bindings is reachable from every one of the 71
functions, so there is no enforced boundary between "multiplayer session state" and "replay playback
state" and "single-player campaign state" — they are one namespace. `testing.md` already notes the
consequence for tests: `buildIndexDom()` "rebuilds `index.html`'s exact structure (kept in sync by
hand — `main.ts`'s `requireElement()` calls run at module-load time and throw immediately against an
empty document)". Any test of any part of `main.ts` pays for all 65 lookups.

**Fix — one concrete seam, not a rewrite.** The multiplayer panel is already the most separable
cluster: `createMultiplayerSession` (`main.ts:1230`), `joinMultiplayerSession`,
`startMultiplayerSessionAsHost`, `openMultiplayerLobbyDialog` (`main.ts:1845`), `armNextGuestSlot`
(`main.ts:1129`), `beginMultiplayerLevel`, `renderMultiplayerLobbyList` (`main.ts:1819`),
`setMultiplayerStatus` (`main.ts:1002`), `activateMultiplayerSubtab` (`main.ts:926`), plus their own
DOM handles and the `activeMultiplayerConnection`/`activeMultiplayerSession`/
`multiplayerConnectionState`/`multiplayerConnectionGeneration` state group. That is roughly 800
lines with a narrow interface to the rest (launch a level, tear down an engine), and `src/ui/`
already exists as the home for exactly this kind of module. **Effort: L. Risk: medium** — it is a
big move in the app's least test-covered area; do it alone, and lean on
`verify-multiplayer-connect`/`-netcode`/`-transition` as the regression gate rather than the unit
suite.

#### M9 — `RaycasterEngine` has 137 fields and a 326-line `simulate()`

`src/engine/engine.ts`, 4797 lines. `simulate(dt)` at `engine.ts:2323-2638` (326 lines); the
constructor at 226 lines; `renderNormalFrame()` at 155.

**Fix — a seam the codebase has already drawn for itself.** `perfDebug.ts` instruments `simulate()`
by *named phase* (`input-poll`, `input-actions`, `sim`, `viewmodel`, `firing`, `particle-effects`,
`hud`), and the perf review's §2 call map lists them as discrete units with their own measured costs.
Those phase boundaries are the natural extraction points — `simulate()` becomes an ordered call list
over private phase methods, matching what the profiler already claims the structure is.
**Effort: M. Risk: MEDIUM — read this before starting**: the order of operations inside `simulate()`
is simulation-affecting and lockstep-critical. Every peer replays the identical seeded draw sequence
(`architecture.md`, *Determinism and replay*), so any reordering desyncs multiplayer and invalidates
every replay including `defaultHighscore.ts`. This is a pure move-into-methods refactor with the call
order preserved exactly, or it is not worth doing — and `doc/dev/decisions.md`'s
*Differential decision harness* note describes the right way to prove it: diff old vs. new over a
seeded corpus.

#### M11 — `assertAllRoomsReachable` is documented as dev-time but runs in every production build

`src/map/generation/pathing.ts:62-63`:
> Dev-time safety net: every room's center should be reachable from spawn …

`src/map/mapGenerator.ts:397` calls it unconditionally, at the end of every `generate()`. There is no
`import.meta.env.DEV` guard, unlike the `?perfDebug=1` pattern used elsewhere for diagnostics.

It is also the more expensive of the two door-loop BFS passes — `pathing.ts:84-100` runs a full-grid
`reachableTiles` flood up to `doors.length + 1` times.

**Both readings are defensible and I can't tell which is intended** (see §4). Either the comment is
wrong and this is a shipping invariant check — in which case say so, because the cost is real — or
the guard is meant to be dev-only and is missing its gate. `decisions.md` calls it "a permanent
dev-time BFS assertion", which leans toward the second reading, but "permanent" cuts the other way.

**Fix**: pick one and make the comment and the code agree. **Effort: S. Risk: low** — if it is gated
out of production, note that the `console.error` is then the only signal an unreachable room ever
produces, and nothing else would catch it in a shipped build.

#### M12 — `combatPolicy.mjs`'s `decide()` is 664 lines

`scripts/lib/combatPolicy.mjs:1287-1950`. The single largest function in scope.

Flagged with a strong caveat: this module is the most carefully-guarded code in the repo.
`decisions.md`'s *Approaches Measured and Rejected* records eleven changes to it that were built,
A/B'd and reverted on the numbers, and the module's own doc comment lists the rules that keep it
mechanically liftable into `src/engine/combatPolicy.ts` later (no page, no async, no Node builtins,
all tuning injected, no `Math.random`/`Date.now`, total sorts).

**Recommendation: do not restructure it for size alone.** It has real unit coverage
(`combatPolicy.test.mjs` pins `decide()` per branch), it is pure, and every past attempt to improve
it "obviously" regressed a measured metric. Noted so the next reviewer doesn't propose it as if it
were an oversight. If it is ever split, the split must be branch-preserving and validated by the
matched-scale A/B, not by reading.

#### M13 — Campaign autosave is documented as skipped for a remote workspace; the level-transition save isn't

`src/main.ts:512-518`, `workspaceIsRemote`'s own doc comment:
> Campaign autosave is **skipped entirely** in that case — `persistProgress`'s saved state is only
> ever resumable via "Continue Run", which re-picks a *local* folder through `pickWorkspace()` and
> has no way to re-fetch a remote repo, so saving would just leave a **dead "Continue Run" button
> pointing nowhere**.

That guard exists in exactly one place — `persistProgress` (`main.ts:3175`):
```ts
  if (!workspaceRootName || !currentLevelPath || workspaceIsRemote) return;
```

But `advanceToNextLevel` calls `saveCampaign` **directly**, bypassing it (`main.ts:2769-2788`):
```ts
        // Persist immediately at the transition (not just the throttled
        // in-play autosave) so a tab closed right after advancing still
        // resumes at the new file rather than the one just cleared.
        saveCampaign({
```
Verified: `workspaceIsRemote` appears nowhere in `advanceToNextLevel` (`main.ts:2734-2809`), and
`saveCampaign` itself (`main.ts:3154`) has no guard of its own. Those are the only two call sites.

**The failure sequence**, all verified against the source:
1. Load the Demos campaign or a GitHub repo. Both call `clearCampaignSave()` on load
   (`main.ts:693`, `:770`), which also hides the Continue tab (`main.ts:3168`). Correct so far.
2. Clear any level → `advanceToNextLevel` writes a `CampaignSave` whose `filePath` is a demo/remote
   path. No guard fires.
3. Reload the page. Module init runs `if (loadCampaignSave()) tabContinue.style.display = "";`
   (`main.ts:614`) → **the Continue tab appears**, pointing at a workspace that cannot be re-picked.
4. Clicking it opens the *local* folder picker, fails to find `save.filePath` in whatever the user
   picks, and lands in the `if (!match)` branch (`main.ts:831-838`): warn, clear the save, start a
   fresh run.

So it is self-healing and destroys nothing — but it produces precisely the "dead Continue Run button
pointing nowhere" the design comment says is being prevented, and it costs the player a folder-pick
and a fresh start to discover that.

**Fix**: guard the transition save the same way the throttled one is —
`if (!workspaceIsRemote) saveCampaign({...})` at `main.ts:2772`, or better, route both through one
helper so the guard cannot be bypassed again. **Effort: S. Risk: none** — it only ever suppresses a
write that is already unusable.

### 2.4 Performance — 4(b) generation / repo analysis, 4(c) load path

Per the brief: frequencies are stated as complexity over named inputs, and where I cannot tell
whether something is hot without measuring, I say so and propose the measurement.

#### P1 — `dressCorridors` rescans the whole grid up to 12 times, each scan O(rooms + features) per tile

`src/map/generation/breakup.ts:750, 754, 766` call `findStraightRuns`; the safety-net loop at
`:753` runs up to `MAX_BREAKUP_SAFETY_PASSES` (10, `:79`). `findStraightRuns` (`:150-182`) scans all
rows then all columns — `2 × size²` tile tests — and each test calls `isCorridorFloor`
(`corridors.ts:243-252`), which loops **every room and every feature placed so far**:
```ts
  for (const room of rooms) { if (x >= room.x && ...) return false; }
  for (const room of breakupRooms) { if (x >= room.x && ...) return false; }
```

Worst case per level: `12 × 2 × size² × (rooms + features)`.

**Measured reality on the demo campaign** (`level_maps/metrics.json`): sizes 55–64, 4–6 rooms, 2–3
features. That is ~12 × 2 × 4,096 × 9 ≈ 0.9M cheap comparisons — free, and the safety loop breaks
early (`:755`, `:761`) on any level that converges, which these do.

**The case I cannot answer without measuring** is a large real repo file: `maxSize` is 160
(`mapGenerator.ts:136`) and rooms scale with entity count, so a several-hundred-entity file could
reach 12 × 2 × 25,600 × ~200 ≈ 120M comparisons on one level — plausibly seconds, on the
level-load path.

**Proposed measurement, not a guess.** `scripts/render-level-maps.mjs` already generates every
campaign level and prints per-level metrics. Point it (or a throwaway variant) at a large real source
file — the repo already uses `src/engine/engine.ts` and GitHub-loaded repos as stress inputs
elsewhere — and time `MapGenerator.generate()` alone, broken down per pass. If `dressCorridors`
dominates, the fix is cheap and local: hoist a per-tile `Uint8Array` "is this tile inside any
room/feature" mask, rebuilt once per `findStraightRuns` call instead of scanned per tile, turning the
inner `(rooms + features)` factor into O(1). **Effort: S once measured. Risk: none** — it is a pure
lookup-table substitution for an existing predicate, changing no rng draw and no output.

#### P2 — `placeKeys` and `assertAllRoomsReachable` each run one full-grid BFS per door

`src/map/generation/doorsKeys.ts:97` inside `while (opened.size < doors.length)`, and
`src/map/generation/pathing.ts:85` inside `for (let i = 0; i <= doors.length; i++)`. Both call
`reachableTiles` (`pathing.ts:10-28`), a full flood fill keyed on `"x,y"` strings.

`pickKeySpot` (`doorsKeys.ts:123-137`) then re-parses every reachable tile key per door:
```ts
  for (const k of reachable) {
    if (used.has(k)) continue;
    const [x, y] = k.split(",").map(Number);
```
— a string split plus two `Number` coercions per reachable tile per door.

Same shape as P1: negligible on the demo campaign (`metrics.json` shows 0–4 doors per level; max 4
on `stage03_legacy_api.php`), potentially real on a file with many private/protected methods, since
`placeDoors` locks every one of them (`geometry.ts:73-77`). Same measurement as P1 answers it. If it
does show up, storing `Point`s alongside the key set removes the parse entirely.

#### P3 — `countTopLevelImports` nests `descendantsOfType` inside its own loop

`src/parser/astUtils.ts:586-591`:
```ts
  for (const node of root.descendantsOfType([...importNodeTypes])) {
    if (!node.isNamed || hasAncestorOfType(node, root, bodyNodeTypes)) continue;
    const nested = node
      .descendantsOfType([...importNodeTypes])
```
O(imports × subtree size). Bounded in practice — an import declaration's subtree is small — but it is
the only nested full-subtree walk in the parser, and it runs once per parsed file.
**Low priority; noted for completeness rather than proposed for change.**

#### P4 — Per-entity AST walks nest with their parents'

Each matched entity gets `maxNestingDepth` + `countDecisionPoints` + `countParameters` +
`summarizeSwitchBranches` + `countAllocations` (itself three `descendantsOfType` calls) over *its own
subtree* — `genericParser.ts:159-186`, mirrored in `phpParser.ts:158-184` and `cParser.ts:149-182`.
Because a `class` entity's subtree contains its methods' subtrees, a class-heavy file re-scans the
same nodes once per enclosing entity.

This is inherent to per-entity metrics and the depth is bounded by class nesting (rarely > 2), so the
multiplier is small. **No action proposed** — recorded so the next audit doesn't re-derive it. Note
the codebase already does the one dedup that pays: comment nodes are collected once and shared via
`extractLargeCommentsFromNodes`/`findCommentedOutCodeBlocksFromNodes` (`astUtils.ts:218, 336`).

#### 4(c) — Load / asset path

Nothing found worth a finding. The three things I checked and cleared:
`defaultHighscore.ts` is a lazily-imported chunk that costs a first-time visitor nothing until they
open an empty Highscores dialog (`architecture.md`); the online WAD catalog is fetched at
build time by `scripts/fetch-online-wads.mjs` and served as a static asset, never decoded on the
critical path; `Parser.init()` is memoized once in `parser/runtime.ts` regardless of how many
adapters need it.

## 3. Deliberately not flagged

Checked, understood, and correct as-is. Recorded so the next review doesn't re-derive them.

- **`MapGenerator.generate()` at 224 lines.** The longest function in the map layer, and it should
  stay one function: its call order *is* the rng draw sequence and therefore the compatibility
  contract for every stored map, replay and highscore. `mapGenerator.ts:14-19` states this. Splitting
  it would obscure the one property that matters most about it.
- **`compressForStorage` (`storageCompression.ts:91`) is unused by production code.** Its own doc
  comment says so and explains why it stays: its inverse `decompressFromStorage` still reads `gz1:`
  boards from older builds, and "deleting this half alone would leave a decoder for a format nothing
  can produce." Correct.
- **Silent `catch { continue }` in `loadWad.ts:118-120` and `:131-133`.** The only truly unlogged
  catches in the WAD layer, but the enclosing doc comment (`:101-104`) documents the skip, and
  `npm run report:wad-stylesets` provides "a per-candidate decode probe" — the diagnostic exists, it
  just lives in the tooling rather than the runtime.
- **The `catch { return <default> }` family across `main.ts:3149/3165/3203/3224/3248`,
  `highscores.ts:116/181`, `storageCompression.ts:98`, `pathSprites.ts:66/133`.** All are
  `localStorage`/capability probes where the fallback *is* the correct behaviour, all carry an
  explanatory comment. Logging them would be noise on every private-browsing session.
- **"Never a hard failure" placement passes logging nothing when a feature finds no space.** Looks
  like a silent-degradation problem; it is a stated, uniform convention with a real gate —
  `npm run verify:campaign` fails when any feature stops appearing anywhere in the campaign.
- **`multiplayerSessionHost.ts` / `multiplayerSessionGuest.ts` structural mirroring** (the ~55-line
  `MultiplayerSessionHandle` getter blocks at `:718-778` / `:531-582`). Genuinely parallel, but the
  divergences are semantic, not accidental — `getConnectionStats` differs because the host holds a
  `Map` of guest links and a guest holds one connection; `getReconciliationCorrections` is hardcoded
  empty host-side with a comment explaining only a guest can observe it. A shared abstraction would
  need a role flag threaded through most getters. **Recommend leaving it.**
- **`spread()` duplicated in `run-balancing-telemetry-multiplayer.mjs:651`.** Its doc comment
  explicitly declares it a deliberate local duplicate because the source module doesn't export it.
- **`Math.random()` in the engine.** Confined to cosmetic randomness (blood scatter, SFX pitch, BGM
  shuffle, console hints) by an explicit, documented rule; simulation randomness goes through seeded
  `mulberry32`. Verified the split holds.
- **`beginPath`/`rect`/`clip` in `renderMinimap:846-848` and the automap.** Looks like exactly the
  path geometry the perf audit banned. It isn't — §6 of that audit measured an axis-aligned rect
  clip as free (Skia takes it as a scissor), and `renderCost.test.ts` deliberately permits path
  *building*.
- **Per-frame allocation churn** in `renderWorldBillboards` and `shadedTexel`. Real, and correctly
  judged Low twice already (perf review P6: zero main-thread GC events in an 8-second traced window).
- **The `/* v8 ignore next -- @preserve */` comments.** Each carries a proof of unreachability rather
  than a "can't test this", and `testing.md` documents the verification procedure required before
  adding one. Spot-checked several; the reasoning holds.
- **The whole per-frame render path.** Audited 2026-08-02, out of scope by agreement.
